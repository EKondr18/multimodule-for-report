# Мультимодульная система обработки данных для отчётов

Веб-приложение со вкладками. Каждая вкладка — отдельный модуль обработки
csv/excel-выгрузок: загрузка файла → обработка → пополнение общего файла
(хранится в `data/<модуль>/...` в этом репозитории) либо генерация таблицы
для копирования.

## Структура

```
backend/            # FastAPI — общий для всех модулей
  app/
    core/            # общая инфраструктура (запись/чтение файлов в GitHub)
    modules/
      baggage_norm/      # модуль 1: «Норматив выдачи багажа»
      baggage_comments/  # модуль 2: «Добавление комментариев по багажу»
      quality_report/    # модуль 3: «Отчёт по качеству»
frontend/            # React + TS + Vite — общий UI, вкладки
  src/
    tabs.ts          # реестр вкладок — новый модуль добавляется одной строкой
    pages/           # страница на каждый модуль
data/
  baggage_norm/      # данные модуля «Норматив выдачи багажа» (master.csv, datalens.csv)
docker-compose.yml
```

## Модуль 1 — «Норматив выдачи багажа»

Вход: еженедельная выгрузка BI МАВ по обработке багажа (xlsx, структура
фиксирована — 8 строк шапки + 29 колонок; имя файла не важно).

Обработка (см. `backend/app/modules/baggage_norm/processing.py`):
1. Определение авиакомпании по префиксу номера рейса.
2. Расчёт статуса выдачи багажа (до 30 мин / 30–40 мин / более 40 мин /
   некорректные отметки / не определено).
3. Объединение с архивом `data/baggage_norm/master.csv`, дедупликация по
   `(date, flight, mc)`.
4. Обновлённый архив и производный 4-колоночный файл (`date, company,
   bag_status, flight`) — `data/baggage_norm/datalens.csv` — коммитятся
   обратно в репозиторий через GitHub API при каждой загрузке.

Пользователю отдаётся `datalens.csv` для DataLens — с предпросмотром,
динамическими фильтрами по колонкам и кнопкой скачивания csv.

## Модуль 2 — «Добавление комментариев по багажу»

Переключатель станции VKO/TBS (по умолчанию VKO).

### VKO

Вход (два окна загрузки):
1. «Норматив выдачи багажа» — csv в формате `datalens.csv` модуля 1 (нужны
   колонки `date`, `flight`; колонки `company`, `bag_status` идут в вывод
   без изменений).
2. «События по выдаче» — excel-выгрузка с колонками `Комментарий`,
   `Дата рейса`, `Номер рейса`.

Обработка (см. `backend/app/modules/baggage_comments/processing.py`):
1. Из excel берётся только дата (без времени) из `Дата рейса`.
2. Сопоставление построчно по `date = Дата рейса` и `flight = Номер рейса`
   — номера рейсов сравниваются по нормализованному ключу (без пробелов, в
   верхнем регистре), т.к. в двух источниках разное написание («ДР 794» /
   «ДР794»).
3. Если на один рейс несколько комментариев — объединяются через запятую.

На выходе — 5 колонок (4 из csv + `comment`) с предпросмотром, фильтрами по
колонкам и скачиванием в виде excel-файла.

### TBS

Вход (два окна загрузки, оба excel):
1. «Рейсы из TBS (прилет)» — берутся колонки `Дата/Время рейса` (только
   дата) и `Номер рейса`.
2. «События по багажу» — берутся колонки `Дата рейса` (только дата),
   `Номер рейса`, `Комментарий`.

Сопоставление по дате рейса и нормализованному номеру рейса (как в VKO).

Из свободного текста `Комментарий` извлекается количество мест багажа и
классифицируется в одну из двух колонок:
- **«Багаж с повреждением»** — по умолчанию: голое число/«N м/б», явное
  упоминание повреждения, «мокрое» и т.п.
- **«Багаж с признаками доступа к содержимому»** — если в комментарии
  упомянут «доступ» (к содержимому).

Если в одном комментарии перечислено несколько мест с разной
классификацией («1 м/б с повреждением, 2 м/б с доступом к содержимому»),
каждое число разбирается отдельно по тексту до следующего числа. Если в
одном фрагменте упомянуты оба признака одновременно («с доступом к
содержимому, с повреждением» без разделения на части) — количество
добавляется в обе колонки. Для комментариев без формата «N м/б» (например,
«СП с повреждением. AKE10933. AKE5514. ...») количество мест оценивается по
числу перечисленных номеров контейнеров/ULD.

На выходе — 4 колонки (`Дата рейса`, `Номер рейса`, `Багаж с повреждением`,
`Багаж с признаками доступа к содержимому`) с предпросмотром, фильтрами и
итоговой строкой с суммой по каждому числовому столбцу. В предпросмотре
показываются все рейсы, а в скачиваемый excel-файл попадают только рейсы,
где хотя бы одна из этих двух колонок не равна нулю.

Оба режима модуля 2 не хранят данные в репозитории — разовое объединение
двух загруженных файлов без накопления истории.

## Модуль 3 — «Отчёт по качеству»

На вход модуль принимает (в перспективе) 5 excel-выгрузок: «Нарушения на
перроне», «Нарушения в АВК», «Проверки PAB», «Проверки GRH», «Мониторинг
LIR/СЗВ». Пользователь задаёт период (даты «с» и «по») и срез агрегации
**Неделя / Месяц / Квартал / Год**, общий для всех таблиц модуля — никакого
деления на разделы (Нарушения/Проверки/Мониторинг) нет, все таблицы
выводятся вместе на одной странице.

Каждая таблица строится из того, что фактически загружено: можно загрузить
любое подмножество из 5 файлов (вплоть до одного), и таблицы заполняются
теми данными, для которых хватает входов. Если конкретной таблице (или, как
в таблице 3, отдельной её колонке) не хватает нужного файла — вместо данных
выводится «Файл не загружен» (см. `NOT_UPLOADED` в
`backend/app/modules/quality_report/processing.py`).

Рядом с каждой сформированной таблицей — кнопка копирования (TSV в буфер
обмена, для вставки в Excel), см. `frontend/src/components/SummaryTable.tsx`.
Строки в детализирующих таблицах (1.1, 2.1) отсортированы по дате от старых
к новым.

Агрегация по срезу — календарная, с привязкой первого периода к началу
заданного диапазона и обрезкой последнего периода по его концу. Для недели
периоды идут блоками по 7 дней от даты начала; для месяца/квартала/года —
по календарным месяцам/кварталам/годам, но первый и последний блок
обрезаются границами заданного диапазона. Например, для периода
08.06.2026–21.06.2026 и срезе «Неделя» получаются ровно 2 строки:
08.06.2026–14.06.2026 и 15.06.2026–21.06.2026 (см.
`backend/app/modules/quality_report/processing.py`, `generate_buckets`).

Таблица 1 — **«Алкогольное/ наркотическое опьянение»** (файлы «Нарушения на
перроне» и «Нарушения в АВК»): подсчёт количества строк с категорией
(колонка `Категория`) «Алкогольное и наркотическое опъянение» в загруженных
файлах за период, с разбивкой по выбранному срезу. Колонки на выходе:
`Период`, `Кол-во`. Рядом — информационная таблица 1.1 со списком
`Дата`/`Описание`/`Исполнитель`/`Подразделение` по всем строкам этой
категории.

Таблица 2 — **«Установка ВС не по разметке»** (только файл «Нарушения на
перроне»): строки с `Категория` = «Встреча ВС на МС» и `Подкатегория` =
«Установка ВС на допустимые точки» классифицируются по колонке `Причина` на
три причины — «Несвоевременное торможение КВС», «Невозможно оценить (вне
ракурса СОК)» и «Вина АООПО» (всё остальное, кроме пустых значений) — и
считаются по периодам. Колонки на выходе: `Период` + по одной колонке на
каждую причину. Рядом выводится информационная таблица 2.1 со списком
`Дата`/`Описание`/`Исполнитель`/`Подразделение` по строкам, попавшим в «Вина АООПО».

Таблица 3 — **«Мониторинг корректности процедур РПО»**: колонка `Кол-во
проверок` — количество строк листа «РПО» файла «Проверки GRH» за период;
колонка `Кол-во замечаний` — количество строк файла «Нарушения на перроне» с
`Подкатегория` = «Руководство подъездом /отъездом;» и `Заключение` = «с
виной» за тот же период. Колонки на выходе: `Период`, `Кол-во проверок`,
`Кол-во замечаний`. Эти две колонки зависят от разных файлов, поэтому
каждая может независимо показывать «Файл не загружен».

Таблица 4 — **«Мониторинг ношения ФО и СИЗ»** (по аналогии с таблицей 3):
колонка `Кол-во проверок` — количество строк листа «ФО и СИЗ» того же файла
«Проверки GRH» за период; колонка `Кол-во замечаний` — количество строк
файла «Нарушения на перроне» с `Подкатегория` ∈ {«Нарушение ФО», «Нарушение
элементов корпоративного стиля», «Соблюдение СИЗ»} и `Заключение` = «с
виной» за тот же период (категория не фильтруется — у каждой из этих
подкатегорий уникальное соответствие категории во входных данных). Один и
тот же загруженный файл «Проверки GRH» используется для обоих листов
(«РПО» и «ФО и СИЗ») — пользователь загружает его один раз.

Таблица 5 — **«Нарушения техники безопасности и охраны труда»** (только файл
«Нарушения на перроне»): построчный (без агрегации по периодам) список
строк с `Категория` = «Техника безопасности, охраны труда», попавших в
выбранный период, отсортированный по дате от старых к новым. Колонки на
выходе: `Дата`, `Категория`, `Описание`, `Место`, `Исполнитель`,
`Подразделение`. Колонка `Место` собирается из колонок `Место` и `Б/Н`
исходного файла через пробел; если значение `Место` состоит только из
цифр, к нему спереди добавляется «МС» (например, `37` → `МС37`).

## Запуск локально

```bash
export GITHUB_TOKEN=<токен с правом записи в репозиторий>
docker compose up --build
```

- Backend: http://localhost:8000/docs
- Frontend: http://localhost:5173

### Переменные окружения backend

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `GITHUB_TOKEN` | токен с правом записи в репозиторий (обязателен) | — |
| `GITHUB_REPO` | `owner/repo`, куда писать данные | `EKondr18/multimodule-for-report` |
| `GITHUB_BRANCH` | ветка для коммитов с данными | `main` |

## Разработка без Docker

```bash
# backend
cd backend && pip install -r requirements.txt
uvicorn app.main:app --reload

# frontend
cd frontend && npm install && npm run dev
```

## Деплой на Vercel (два отдельных проекта)

**Backend** (`backend/`):
1. New Project → импортировать этот репозиторий → **Root Directory** = `backend`.
2. Vercel сам распознает `api/index.py` (serverless-функция, экспортирует FastAPI-приложение)
   и `vercel.json` (роутит все пути в эту функцию — маршрутизацией внутри занимается FastAPI).
3. Settings → Environment Variables → добавить `GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_BRANCH`.
4. Deploy. Получите URL вида `https://<backend-project>.vercel.app`.

**Frontend** (`frontend/`):
1. New Project → тот же репозиторий → **Root Directory** = `frontend`.
2. Framework Preset — Vite (определится автоматически).
3. Settings → Environment Variables → `VITE_API_BASE_URL` = URL backend-проекта из шага выше
   (без слэша на конце, например `https://reports-backend.vercel.app`).
4. Deploy.

Локально `VITE_API_BASE_URL` не нужен — Vite dev-сервер проксирует `/api/*` на
`http://localhost:8000` (см. `vite.config.ts`), это покрывает запуск через
`docker compose` или `npm run dev`.

## Известное ограничение

Запись файлов идёт через GitHub Contents API. Поле `content` в ответе этого
API пустое для файлов больше ~1 МБ — для таких файлов чтение автоматически
переключается на Git Blobs API (см. `backend/app/core/github_storage.py`),
у которого лимит — 100 МБ. Если архив вырастет за этот предел, нужно будет
переходить на Git LFS.

Backend развёрнут на always-on хостинге (Render/аналог), поэтому жёсткого
лимита времени на запрос, характерного для serverless-функций (как на
Vercel Hobby — 10 сек), здесь нет.
